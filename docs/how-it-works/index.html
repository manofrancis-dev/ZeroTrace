Scanning methodology

How Zero Trace scans a URL

A scan is a sequence of checks, not a single lookup. This page explains what happens after you press “Deep Scan,” what each provider contributes, and where the evidence can be incomplete.

Updated 27 November 20265-stage pipelineBounded scan window

Zero Trace is a server-side URL analysis application. The browser interface collects the URL; the backend validates it, queries external services, runs an isolated browser, and returns a structured report. The frontend does not replace a failed live scan with a local guess.

Step 1 — URL validation and SSRF protection

The backend first normalizes the input and restricts it to HTTP or HTTPS. It rejects scheme-like values such as javascript:, data:, and mailto:. It also enforces a maximum URL length and requires a hostname.

Before any provider or sandbox request, the host is checked for private, loopback, local, link-local, multicast, and reserved addresses. The check resolves the hostname and rejects destinations that resolve into those ranges. This is SSRF protection: it prevents the scanner from being used to probe internal services.

If the URL contains a username or password, those credentials are stripped before the URL is sent to VirusTotal, RDAP, or the browser sandbox. The scan endpoint also requires a signed, short-lived session cookie and is rate-limited per client address.

Step 2 — VirusTotal reputation

When a VirusTotal API key is configured, Zero Trace looks for an existing URL report. If fresh submission or reanalysis is enabled, it asks VirusTotal to analyze the URL again and polls a bounded number of times. The public API has request limits, so the fresh-analysis window is intentionally short.

If the fresh analysis completes, the report includes per-engine detections and statistics. If it does not complete, Zero Trace falls back to the current URL report when one exists and labels the result as fallback evidence. If no report exists, the provider state is NO_EXISTING_REPORT. A pending analysis is never presented as clean.

VirusTotal’s documentation says submitted or queried items may be added to its dataset. That is why Zero Trace tells users not to scan confidential URLs.

Step 3 — RDAP registration lookup

Zero Trace queries RDAP for the domain or IP address behind the URL. The report can include registration and expiration events, nameservers, and DNSSEC delegation status. RDAP is contextual evidence: a new domain is not automatically malicious, and an old domain is not automatically safe.

RDAP responses vary by registry. Some fields may be redacted or absent. If the lookup fails, the provider card reports PROVIDER_ERROR or NO_RECORD instead of inventing registration data.

Step 4 — Isolated browser analysis

The URL is opened in an isolated Chromium sandbox. The sandbox records the final URL after redirects, redirect count, HTTP status, page title, response count, download events, file names, sizes, and locally computed SHA-256 hashes. It also reports suspicious page signals that its analysis is configured to detect.

SSRF checks are applied before the scan and to browser requests, including redirects and WebSockets. Because the browser performs its own DNS resolution, a DNS-rebinding domain could still change its answer between checks. The sandbox network isolation is the final boundary.

Websites can block automated browsers or serve different content to scanners. A sandbox result is therefore one layer of evidence, not a complete view of what every visitor will see.

Step 5 — Findings and evidence correlation

The backend combines local URL heuristics, VirusTotal detections, and sandbox signals. Each finding has a severity, title, detail, and source. The score starts from the local URL analysis and applies risk for observed provider and sandbox signals.

Coverage caps keep sparse evidence from looking like certainty. If neither reputation nor browser evidence is available, the score cannot exceed 85. If only one is available, it cannot exceed 94. A score of 100 is intentionally never returned. The verdict is MALICIOUS, SUSPICIOUS, or NO KNOWN THREAT, and the recommendation explains what to do next.

What the progress bar means

The progress bar is an estimate, not a measurement of backend work. It advances while the request is in flight and reaches 100% when the response arrives. A scan can take longer than the animation suggests, especially when VirusTotal is performing a fresh analysis or the backend is waking from a cold start. The result is only shown after the backend responds.

Why scans can fail or return limited evidence

  • Provider not configured: a missing API key produces NOT_CONFIGURED, not a clean result.
  • Provider error or rate limit: the card reports PROVIDER_ERROR with available status information.
  • No existing report: the card reports NO_EXISTING_REPORT and the score is capped.
  • Sandbox blocked: some sites reject automated browsers or serve different content.
  • Private destination: private, loopback, local, multicast, and reserved hosts are rejected by design.
  • Cold start: a hosted backend may need time to wake. Retry after a short wait.

Repeated scans

Every scan creates a fresh browser session and a unique client scan ID. API responses are marked no-store. You can scan one URL, refresh the page, paste a different URL, and repeat the cycle without reusing the previous result. The frontend aborts an older in-flight request when you start a new scan.
