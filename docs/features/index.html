URL security analysis

Malicious URL scanner features

Zero Trace is built around a simple rule: show the evidence, show the gaps, and never turn missing data into a clean verdict. Each scan combines independent sources instead of relying on a single blocklist.

Updated 27 November 20266 evidence layers0–99 evidence score

A URL can look ordinary and still lead to a credential-harvesting page, a fake shop, or a malware download. The opposite is also true: a legitimate site can be new, poorly configured, or briefly compromised. Zero Trace does not try to reduce that complexity to a single “safe” badge. It gathers several kinds of evidence, reports provider status, and explains what the evidence supports.

VirusTotal URL reputation

VirusTotal aggregates URL observations from many security engines. When a VirusTotal API key is configured on the Zero Trace backend, the scanner uses that data as one layer of reputation evidence.

Existing reports and fresh analysis

Zero Trace first looks for an existing URL report. When fresh submission or reanalysis is enabled, it can also ask VirusTotal to analyze the URL again. The fresh-analysis path is deliberately bounded because the public VirusTotal API is rate-limited. If a fresh analysis does not complete within the scan window, the report says so and falls back to existing evidence rather than showing a pending state as if it were clean.

What the provider card shows

The card reports malicious, suspicious, harmless, and undetected counts, along with named engine detections when available. It also shows whether the result came from a fresh analysis or an existing report, and whether a refresh failed or timed out.

Important limits

  • A missing VirusTotal report is shown as NO_EXISTING_REPORT, not as safe.
  • A clean report is reputation evidence, not a guarantee of future behavior.
  • VirusTotal’s documentation says submitted or queried items may be added to its dataset. Do not scan confidential URLs.
  • Zero Trace does not upload downloaded files to VirusTotal and does not perform a VirusTotal file-hash lookup. Downloaded files are hashed locally with SHA-256 for the report.

RDAP domain registration intelligence

RDAP is the structured successor to WHOIS. Zero Trace queries rdap.org for the domain or IP address behind the URL and displays registration context that can help you judge a destination.

What RDAP adds

  • Registration and expiration events for the domain.
  • Nameserver records, which can reveal where DNS is hosted.
  • DNSSEC delegation status when the registry publishes it.
  • IP registration data when the URL uses an IP address as its host.

How to interpret registration age

A recently registered domain is not automatically malicious, and an old domain is not automatically trustworthy. Registration age is context. A brand-new domain asking for payment or credentials deserves more caution, especially when the message that delivered it was unexpected. Privacy redaction can also hide registrant details, so absence of ownership information is not proof of fraud.

Isolated browser analysis

Some URL behavior only appears after a browser opens the page. Zero Trace sends the URL to an isolated Chromium sandbox and records what happens during a bounded visit.

What the sandbox records

  • The final URL after redirects and the redirect count.
  • The HTTP status, page title, and number of responses observed.
  • Download events, file names, sizes, and locally computed SHA-256 hashes.
  • Suspicious page signals that the sandbox is configured to detect.
  • A sandbox verdict and the evidence behind it.

Sandbox limits

Websites can block automated browsers, serve different content to scanners, or change behavior by location and device. That is why the sandbox is one layer, not the final answer. The sandbox is also deployed on an isolated network as a security boundary; DNS rebinding remains a residual risk that the SSRF checks reduce but cannot eliminate.

URL structure and phishing heuristics

Before any provider responds, Zero Trace inspects the URL itself. These checks are signals, not proof, but they can reveal patterns that deserve attention.

  • HTTP instead of HTTPS — the connection is not encrypted.
  • Credential-style @ syntax — the visible host may not be the real destination.
  • Unusual length — long URLs can hide the meaningful part of a destination.
  • Punycode — internationalized hostnames can resemble familiar Latin-script brands.
  • Account-lure terms — words such as login, verify, password, wallet, reset, and payment in the path or query.
  • Redirect-style parameters — parameters commonly used to send visitors elsewhere.
  • IP address hosts — a URL that points directly to an IP address instead of a domain.
  • Executable paths — paths ending in .exe, .scr, .bat, .cmd, .msi, .apk, .dmg, or .iso.
  • Lookalike brand tokens — common character substitutions used to imitate well-known brands.

No single heuristic decides the verdict. The report shows each finding, its severity, and its source so you can judge the combination.

Evidence correlation and scoring

The final score is a 0–99 summary of observed evidence. It is not a probability, and 100 is intentionally never returned. The scanner combines URL findings, VirusTotal detections, and sandbox signals, then applies coverage caps:

  • If neither reputation nor browser evidence is available, the score cannot exceed 85.
  • If only one of those two layers is available, the score cannot exceed 94.
  • RDAP is contextual intelligence, not a threat verdict, so it does not lift the score by itself.
  • Missing reports, provider errors, and missing configuration reduce coverage instead of counting as safe.

The report also shows confidence and how many providers actually reported. That lets you distinguish “no threat found in strong evidence” from “very little evidence was available.”

Security and privacy guardrails

  • SSRF protection: loopback, private, local, link-local, multicast, and reserved destinations are rejected before the sandbox runs.
  • Credential stripping: username and password components are removed before the URL is sent to providers or the browser.
  • Session checks: the scan endpoint requires a signed, short-lived scan session cookie.
  • Rate limiting: the expensive scan endpoint is throttled per client address. Deployments with multiple workers should enforce the same limit at the edge.
  • No-store responses: scan API responses are marked no-store so browsers and intermediaries do not cache them.
  • No scan-history database: Zero Trace does not provide a saved scan history. Third-party services and hosting providers still process data under their own terms.

What Zero Trace does not do

  • It does not guarantee that a URL is safe.
  • It does not perform a full malware scan of your device or of downloaded files.
  • It does not scan authenticated, intranet, or private-network pages.
  • It does not upload downloaded files to VirusTotal or look up their hashes there.
  • It is not a replacement for an antivirus, endpoint protection, or professional incident response.
  • It is not affiliated with VirusTotal, Google, or any security vendor.
